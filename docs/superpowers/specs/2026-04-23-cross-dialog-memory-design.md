# 2026-04-23 项目跨对话记忆设计

## 背景
当前项目需要在多个独立对话中持续推进，但模型本身不提供可靠的项目级永久记忆。为了让每次新对话都能快速恢复上下文，并且让项目状态可审阅、可版本控制、可维护，需要把“项目记忆”外置到仓库文档中。

## 目标
- 让新对话能够快速读取项目现状、关键约束、近期重点和长期决策。
- 让项目记忆以结构化文档存在，而不是散落在聊天记录中。
- 保持方案足够轻量，不引入额外脚本、数据库或自动摘要服务。

## 备选方案

### 方案一：单一记忆文件
- 做法：
  只增加一个根目录 `PROJECT_MEMORY.md`。
- 优点：
  结构最简单，实施成本最低。
- 缺点：
  当前状态与长期决策容易混在一起，后续维护成本会逐步升高。

### 方案二：结构化记忆文件
- 做法：
  增加 `PROJECT_MEMORY.md` 与 `docs/project_memory/decision_log.md`，并在 `AGENTS.md` 中规定读取与回写流程。
- 优点：
  当前状态与历史决策分离，维护成本低，适合当前项目阶段。
- 缺点：
  需要在会话结束时多维护一个文档。

### 方案三：自动化记忆系统
- 做法：
  通过脚本或自动摘要机制在每次会话后自动生成和回写项目记忆。
- 优点：
  理论上最省人工维护。
- 缺点：
  实现和维护成本高，当前收益不足，容易把记忆系统做得比项目本身更复杂。

## 选型
采用方案二，即“结构化记忆文件”。

## 设计

### 文件职责
- `AGENTS.md`
  保存稳定的项目规则，并新增跨对话记忆机制说明，要求新对话优先读取记忆文件。
- `PROJECT_MEMORY.md`
  保存项目当前有效状态，包括目标、目录职责、环境约定、关键约束、当前重点、待办和最近更新。
- `docs/project_memory/decision_log.md`
  保存长期有效的重要决策及其原因与影响。

### 工作流
- 新对话开始时，先读取 `AGENTS.md`、`PROJECT_MEMORY.md` 和 `docs/project_memory/decision_log.md`。
- 完成记忆文件读取后，如果用户请求涉及具体模块、配置或故障，再补充读取与任务直接相关的代码、配置、测试和必要的设计文档。
- 只要本次会话修改了项目，结束前至少更新 `PROJECT_MEMORY.md` 的“最近更新”部分；如果修改还影响项目状态、关键接口、依赖、硬件接入方式、长期约束或风险判断，则同步更新对应内容。
- 只记录提炼后的事实、约束、决策和待办，不保存完整聊天记录。

### 数据边界
- 不记录密钥、许可证、口令、隐私信息或无必要的本机敏感路径。
- 如果记忆文档与代码、配置或更具体文档冲突，以更新且更具体的事实为准，并在会话结束时修正文档。
- 该机制不改变现有项目边界，`control_wangbo/` 继续默认只读。

## 成功标准
- 新对话无需依赖历史聊天，也能从仓库内文档恢复主要上下文。
- 项目当前状态与历史决策有清晰分工，不混写。
- 文档维护负担足够低，能在后续会话中被持续使用。

## 非目标
- 不引入数据库、向量检索或自动摘要服务。
- 不自动扫描整个仓库生成记忆。
- 不替代代码、配置文件和真实测试结果本身作为最终事实来源。
