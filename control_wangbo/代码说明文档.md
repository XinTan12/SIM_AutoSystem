# 控制程序代码说明文档

## 1. 这个项目一句话是做什么的

这是一套用于微流控单细胞实验的上位机控制程序。  
它把界面操作、相机采图、图像识别、单片机串口触发、视频保存、ROI 数据记录这些事情组合在一起，用来实现“看到细胞 -> 判断是否满足条件 -> 控制芯片动作 -> 继续跟踪结果”的自动化流程。

如果用最通俗的话说，这个程序相当于实验设备的“总控大脑”。


## 2. 这套程序控制了什么设备

从代码看，程序主要控制 3 类硬件：

1. 高速相机
用于连续采集主视野图像，做实时识别、触发录像、流速检测、自动筛选判断。

2. sCMOS 相机
用于采集另一条观察通道的图像，代码设计目的是做弹性形变相关判断。

3. 单片机 MCU
通过串口接收上位机命令，控制芯片上的不同 Trigger 通道，比如 `Capture`、`Release`、`Sort`、`ElasticityMeasurement`。

程序和这些硬件的关系可以理解成：

- `main.py` 负责“总控调度”
- `FastCameraThread.py` 负责“高速相机采图 + 图像识别”
- `sCMOSCameraThread.py` 负责“第二路相机采图 + 弹性判别”
- `MCUTriggerThread.py` 负责“把动作命令发给单片机”
- `PublicClassCamera.py` 负责“缓存图像和保存视频”


## 3. 目录与关键文件说明

这个文件夹里最关键的文件如下：

### `main.py`

整个程序的主入口。  
负责创建窗口、初始化按钮、读取参数、连接线程、更新界面、接收图像处理结果、记录数据、控制自动流程开关。

### `CellSorting_ui.py`

Qt Designer 自动生成的界面代码。  
它主要负责“界面长什么样、有哪些控件”，不是核心业务逻辑文件。

### `CellSorting_ui.ui`

界面设计源文件。  
如果以后要改界面布局，通常先改这个文件，再重新生成 `CellSorting_ui.py`。

### `FastCameraThread.py`

高速相机相关核心逻辑：

- 连接 MindVision 相机
- 连续采集 16 位灰度图
- 把图像放进环形缓冲区
- 按 ROI 做图像分析
- 判断是否触发自动流程
- 保存触发前后视频
- 做流速估算

### `MCUTriggerThread.py`

单片机串口控制逻辑：

- 打开和关闭串口
- 把 UI 参数转成 MCU 可理解的字节命令
- 下发 `Capture / Release / Sort / ElasticityMeasurement`
- 接收图像识别结果后推进自动筛选状态机

### `sCMOSCameraThread.py`

sCMOS 相机相关逻辑：

- 连接 PCO 相机
- 连续采集 16 位图像
- 保存触发前后图像
- 提取弹性测量 ROI 的背景
- 对指定帧做形变长度判定

### `PublicClassCamera.py`

公共组件：

- `RingBuffer`：环形缓存，保存最近一段时间的图像
- `TriggerBuffer`：记录 trigger 前后的帧索引
- `VideoSaver`：根据帧索引把图像保存成 AVI 或 TIFF

### `lastConfiguration.json`

程序退出时自动保存、下次启动时自动加载的默认参数文件。  
也就是说，界面上的很多设置不是每次手动重新输入，而是从这个文件恢复。


## 4. 整体架构图解

可以把程序分成 4 层：

### 4.1 UI 层

由 `main.py` 和 `CellSorting_ui.py` 组成。  
作用是显示界面、接收按钮操作、显示实时图像和统计结果。

### 4.2 设备层

负责直接和硬件通信：

- 高速相机：`FastCameraWorker`
- sCMOS 相机：`sCMOSCameraWorker`
- MCU 串口：`MCUTriggerWorker`

### 4.3 算法层

负责看图、找细胞、做判断：

- 高速相机 ROI 处理：`FastCameraThread.py` 中的 `ImageProcessor`
- sCMOS 弹性判定：`sCMOSCameraThread.py` 中的 `ImageProcessor`

### 4.4 数据层

负责缓存和落盘：

- 图像缓存：`RingBuffer`
- 触发缓存：`TriggerBuffer`
- 视频保存：`VideoSaver`
- ROI 表格记录：`main.py` 中的 `roi_data_queue`

可以把整体数据流理解成下面这样：

```text
用户在界面改参数 / 点按钮
        ↓
main.py 收集参数并发给各线程
        ↓
相机线程持续采图 -> 图像进入环形缓冲区
        ↓
图像处理线程按 ROI 做识别
        ↓
识别结果发回 main.py 和 MCU 线程
        ↓
MCU 线程决定是否发送 Capture / Release / Sort 等命令
        ↓
触发前后图像按需要保存为视频/图像/数据表
```


## 5. 程序启动后发生了什么

程序从 `main.py` 的最后几行启动：

1. 创建 `QApplication`
2. 创建 `MainWindow`
3. 调用 `UI_Init()` 绑定各个按钮和控件
4. 自动扫描串口和高速相机
5. 如果根目录存在 `lastConfiguration.json`，就自动加载上次参数
6. 显示主界面

此时程序还没有真正开始采图。  
真正开始工作的顺序通常是：

1. 点击连接 MCU
2. MCU 串口打开成功
3. 程序自动去连接高速相机
4. 如果用户另外点击 sCMOS 连接，再启动 sCMOS 相机线程
5. 用户再决定是否进入图像处理模式、视频保存模式、自动筛选模式等


## 6. 三条主线详解

## 6.1 高速相机主线

对应文件：`FastCameraThread.py`

### 职责

- 连接高速相机
- 连续取帧
- 计算显示帧率
- 把图像送去做 ROI 分析
- 根据 trigger 缓存保存视频

### 输入

- 相机型号和设备信息
- 曝光时间、帧率、增益、ROI 大小
- 图像处理参数
- 是否进入视频保存模式

### 输出

- 最新帧索引和 FPS，发回 UI 显示
- 某一帧需要进入图像处理的信号
- 触发前后需要保存的视频帧索引

### 内部逻辑

`FastCameraWorker.run()` 会不断做这几件事：

1. 初始化 MindVision 相机
2. 设成连续采集模式
3. 设置 ROI、曝光、增益、帧率、16 位输出格式
4. 持续从相机取图
5. 把图像转成 `numpy` 数组
6. 放进 `RingBuffer`
7. 如果开启图像处理，就把当前帧索引发给图像处理线程
8. 如果开启视频保存模式，就往 `TriggerBuffer` 中累积前后帧
9. 以较低频率把当前帧显示到界面，避免 UI 太卡

这里最重要的设计不是“保存每一张图”，而是“始终循环缓存最近很多帧”。  
这样当触发事件出现时，程序不仅能保存触发后的图，还能把触发前已经经过的画面一起保存下来。


## 6.2 MCU 串口触发主线

对应文件：`MCUTriggerThread.py`

### 职责

- 打开串口
- 把界面里的时间参数转换成 MCU 命令
- 在不同阶段向芯片下发不同 Trigger
- 根据图像识别结果推进下一步

### 输入

- 串口号和串口参数
- Capture / Release / Sort / ElasticityMeasurement 的持续时间
- 图像处理线程返回的识别结果

### 输出

- 串口字节命令
- 通知 UI 某个 Trigger 已结束
- 通知图像处理线程切换到下一个 ROI 模式

### 内部逻辑

程序把不同动作编码成 2 字节命令，例如：

- `0xFE`：Capture
- `0xFD`：ElasticityMeasurement
- `0xFB`：Release
- `0xF7`：Sort

第 2 个字节通常表示触发持续时间。  
如果写成 `0xFF`，表示长时间保持，不自动结束，代码里把这类模式用于手动冲洗通道。

这个文件里最关键的不是“发送串口”本身，而是 `slot_finish_ROI_processing()`。  
它相当于自动筛选的状态机：上一阶段图像识别完成后，这里决定下一步该做什么。


## 6.3 sCMOS 主线

对应文件：`sCMOSCameraThread.py`

### 职责

- 连接 sCMOS 相机
- 连续采集 16 位图像
- 保存 sCMOS 图像
- 获取弹性 ROI 的背景图
- 对某一帧进行弹性形变判定

### 输入

- sCMOS 相机 ROI、曝光、延迟等参数
- 弹性 ROI 位置
- 二值化阈值、最小面积、长度上下限
- 指定要分析的帧索引

### 输出

- sCMOS 当前帧和 FPS 给 UI
- 指定 ROI 的背景更新结果
- 弹性分析后的判断结果

### 内部逻辑

`sCMOSCameraWorker.run()` 会不断从 PCO 相机取最新图像，并放入自己的 `RingBuffer`。  
当某些标志位被置为 `True` 时，它会额外做两件事：

1. 发送“背景更新帧索引”
在 Capture 触发后，取当前帧前第 5 帧作为背景候选。

2. 发送“弹性分析帧索引”
设计意图是：弹性动作结束后，拿某一帧 ROI 图像来分析细胞形变程度。

### 需要特别说明的一点

从当前实际代码看，`MCUTriggerThread.py` 里启用的是“单相机测试版本”的 `slot_btn_triggerElasticityMeasurement()`。  
也就是说，当前启用代码会执行弹性通道动作，但**不会自动发出 `signal_sCMOS_enterImageProcessor`**。  
文件里确实保留了“双相机版本”的实现，但它被放在注释中，没有启用。

这意味着：

- 代码结构上已经为双相机联动预留了接口
- 但当前启用逻辑更接近“手动判断是否目标细胞”的测试状态
- 文档里看到的“双相机设计目标”和“当前正在跑的行为”不能完全等同


## 7. 自动筛选主流程逐步解释

自动流程的核心逻辑主要写在 `MCUTriggerThread.py` 的注释和 `slot_finish_ROI_processing()` 中。

可以把整个流程看成下面 6 步。

### 第 1 步：Capture

程序在高速相机的 `cellFlowThrough ROI` 中持续找细胞。  
当它发现：

- 只有 1 个目标轮廓
- 面积在合理范围内
- 形状接近圆
- 不贴边
- 位置落在 Capture ROI 要求区域

就认为这是一个适合被捕获的细胞，于是：

1. 通知 MCU 发 `Capture Trigger`
2. 通知 sCMOS 更新背景候选
3. 等待一段 `trappedIntervalTime`
4. 切换到 `Trapped ROI` 分析

### 第 2 步：Trapped

程序检查陷阱区里有没有成功抓住细胞。

- 如果有合格细胞，进入下一步
- 如果没有
  - 连续模式：执行 `Release`，再回到 Capture 重新找下一个
  - 单次模式：停止本轮自动流程

### 第 3 步：ElasticityMeasurement

设计目标是让细胞经过弹性相关处理，再根据 sCMOS 图像判断是不是目标细胞。

但当前启用代码中，这一步的“自动 sCMOS 分析联动”并没有完全打开。  
实际运行上更接近：

- 执行弹性通道触发
- 触发结束后允许 UI 侧根据勾选框 `chb_isTarget` 做手动目标判定

如果未来启用注释里的双相机版本，这一步才会真正自动调用 sCMOS ROI 分析。

### 第 4 步：Release

如果细胞被判定为目标细胞，程序会先监视 `Release ROI`。  
只有当释放路径里“没有细胞堵着”时，才执行 `Release Trigger`，让目标细胞继续向后走。

### 第 5 步：Sort

程序监视 `Sort ROI`，在限定时间窗口内寻找目标细胞。

- 找到：执行 `Sort Trigger`
- 没找到：
  - 连续模式回到前面重新开始
  - 单次模式结束

### 第 6 步：Collected

最后监视 `Collected ROI`，看分选后的目标细胞是否真的到了收集区域。

- 看到细胞：认为本轮成功
- 超时还没看到：记一次 miss

如果开启了 miss event 保存模式，还会额外把失败前的一段视频保存下来，方便事后分析。


## 8. ROI 的含义与分工

ROI 可以理解成“只盯着图像里的一个小窗口看”。  
程序不是对整张图做同一种判断，而是对不同区域做不同任务。

### `cellFlowThrough ROI`

主流道观察区。  
用于 Capture 前看细胞是否经过，也用于 Release 前看通道里是否已经清空。

### `capture ROI`

是 `cellFlowThrough ROI` 里的一个更严格小区域。  
程序只在这里要求“一个合适的细胞刚好到位”，这样可以减少误吸多个细胞。

### `trapped ROI`

看细胞是否真的被困住或贴住指定位置。

### `sCMOS elasticityMeasurement ROI`

给 sCMOS 相机看的区域，用于弹性形变长度判断。

### `sort ROI`

目标细胞释放后向下游移动，程序在这里等它出现，再决定是否触发分选。

### `collected ROI`

分选完成后的收集验证区，用于确认结果是否真的到达。

### `flowRate ROI`

专门用于测速。  
程序记录同一细胞在两次观察中的位置差和时间差，然后估算细胞速度与流量。


## 9. 参数和配置文件在控制什么

参数主要来自界面控件，程序会在 `update_image_processing_para()` 和 `updata_MCU_tirgger_para()` 中汇总发送给各线程。

### 相机类参数

- ROI 宽高
- 曝光时间
- 帧率
- 增益
- 环形缓冲大小
- 触发前后要保存多少帧

### 图像处理类参数

- 二值化阈值
- 最小面积、最大面积
- sCMOS 最小面积
- sCMOS 形态学核大小
- 开运算、闭运算次数
- 弹性长度上下限

### 动作控制类参数

- Capture 持续时间
- Release 持续时间
- Sort 持续时间
- ElasticityMeasurement 持续时间
- Capture 后等待完全陷获的时间

### 流速换算类参数

- 芯片通道宽度
- 芯片通道高度
- 物镜倍数
- 采样帧数

### `lastConfiguration.json` 的作用

这个文件就是“上次退出前的默认设置快照”。  
程序启动时如果发现它存在，就自动恢复大部分关键参数。  
程序关闭时又会把当前参数重新保存回去。

这意味着它不是实验结果文件，而是“软件的默认工作配置”。


## 10. 数据保存与输出文件说明

程序会生成几类输出文件。

### `YYYYMMDD_video`

保存触发前后的视频文件。

- 高速相机通常保存成 `.avi`

文件名里会拼入：

- miss 计数
- 算法耗时
- 间隔时间
- 细胞面积
- 质心坐标
- 当前处理阶段
- 时间戳

### `experiment_info_xxx.txt`

保存实验备注文本，由界面里的实验说明文本框导出。


## 11. 用通俗语言解释关键实现机制

## 11.1 PyQt 界面

PyQt 是这个程序的桌面界面框架。  
你看到的按钮、输入框、标签、图像显示框，几乎都来自这里。

### 11.2 线程

线程可以理解成“并行干活的工人”。

为什么这个程序必须多线程：

- 相机采图必须一直跑，不能被界面卡住
- 图像处理比较耗时，不能堵住采集
- 视频保存也不能阻塞采图
- 串口通信最好也独立出去

所以代码把不同工作拆成多个线程：

- UI 主线程
- 高速相机采集线程
- 高速相机图像处理线程
- 高速相机视频保存线程
- sCMOS 采集线程
- sCMOS 图像处理线程
- sCMOS 保存线程
- MCU 串口线程

### 11.3 信号槽

这是 PyQt 里线程之间通信的常用方式。  
可以理解成：

- 一个线程“发消息”
- 另一个线程“收到消息后执行函数”

例如：

- 相机线程发“当前帧索引”
- 图像处理线程收到后开始分析
- 图像处理线程发“发现目标细胞”
- MCU 线程收到后执行 Capture

### 11.4 环形缓冲区

`RingBuffer` 就像一个固定大小的循环仓库。  
新图像来了就放进去，仓库满了就覆盖最旧的图。

这样做有两个好处：

1. 内存不会无限增长
2. 触发事件发生后，能立刻把“前几帧”和“后几帧”都找出来保存

### 11.5 背景差分

程序不是直接找“亮的东西”或“黑的东西”，而是把当前图像和背景图做差。

简单说就是：

```text
当前图像 - 背景图 = 发生变化的位置
```

这样更容易突出“新出现的细胞”或者“细胞带来的亮度变化”。

### 11.6 阈值

差分之后，程序还要决定“多大变化才算是真的目标”。  
这个门槛就是阈值。

- 太低：噪声也会被当成细胞
- 太高：真实细胞可能被漏掉

### 11.7 形态学处理

图像里经常会有小噪点、孔洞、边缘不完整。  
代码使用开运算、闭运算来让轮廓更干净，再去找外轮廓。

你可以把它理解成“先擦掉小杂点，再把轮廓补平整”。


## 12. 一次典型实验的时序示例

下面给出一轮自动筛选的简化时序：

```text
程序启动
  ↓
连接 MCU 成功
  ↓
自动连接高速相机
  ↓
用户提取背景图
  ↓
用户进入图像处理模式
  ↓
用户开启连续筛选
  ↓
高速相机持续看 cellFlowThrough ROI
  ↓
发现 1 个合适细胞 -> MCU 发 Capture
  ↓
等待 trappedIntervalTime
  ↓
检查 trapped ROI
  ↓
若抓住细胞 -> 执行 ElasticityMeasurement
  ↓
若判定为目标细胞 -> 等待 Release ROI 清空
  ↓
MCU 发 Release
  ↓
等待目标细胞出现在 Sort ROI
  ↓
MCU 发 Sort
  ↓
检查 Collected ROI 是否看到细胞
  ↓
记录成功或 miss，进入下一轮
```


## 13. 目前代码里的局限、风险和阅读注意点

这部分很重要，因为“代码想做的事情”和“当前真正启用的事情”并不完全一致。

### 13.1 双相机弹性联动没有完全启用

代码里保留了双相机版的 `slot_btn_triggerElasticityMeasurement()`，  
但当前启用的是“单相机测试版本”。

这意味着：

- 界面和线程连接已经为 sCMOS 联动留好了很多接口
- 但自动流程里真正触发 sCMOS 进入弹性分析的信号，目前在启用代码路径中没有发出

### 13.2 部分命名和实际行为存在历史痕迹

例如：

- `sCMOS` 相关接口已经存在，但流程并非全自动闭环
- 注释里写的是一种实验逻辑，实际启用代码可能是测试版
- 某些单位注释和换算含义需要结合实验实际再确认

所以阅读时要优先相信“正在执行的代码”，其次再看注释。

### 13.3 `CellSorting_ui.py` 很大，但不等于核心逻辑复杂

这个文件很长，主要是因为界面控件很多，而且是自动生成的。  
不要被它的体积吓到。真正值得重点理解的是 `main.py`、三个线程文件和公共缓存文件。

### 13.4 图像算法目前是规则法，不是机器学习

当前识别主要靠：

- 背景差分
- 阈值
- 面积过滤
- 圆度过滤
- 长宽比过滤
- 与边界的关系

它的优点是直观、可调。  
缺点是对参数、背景质量、成像稳定性比较敏感。

### 13.5 流程对参数正确性依赖很强

只要下面这些参数设置不合理，流程就可能误判：

- ROI 画得不准
- 背景提取得不好
- 阈值太高或太低
- 面积范围不对
- Trigger 时间和流体实际响应不匹配


## 14. 术语表

### 上位机

就是运行这套界面软件的电脑程序。

### MCU

单片机。  
这里主要负责接收串口命令并控制实际的芯片触发动作。

### Trigger

一次动作触发命令，比如打开某一路压力、阀门或控制通道一段时间。

### ROI

Region of Interest，感兴趣区域。  
就是程序只盯着图像中的一个小矩形区域做判断。

### RingBuffer

环形缓冲区。  
固定容量、循环覆盖的图像缓存。

### pre-trigger / post-trigger

触发前保存多少帧、触发后保存多少帧。

### 背景差分

用当前图像减去背景图，突出发生变化的位置。

### 形态学开运算 / 闭运算

图像清理手段，用来去小噪声、补轮廓。

### 圆度

轮廓有多接近圆形。  
程序用它来帮助判断是不是单个细胞。

### trapped

表示细胞已经被困在预定位置。

### collected

表示细胞已经到达最后收集区域。


## 15. 如果你接下来要继续读代码，建议先看哪里

如果你完全不懂代码，建议按这个顺序看：

1. 先看 `main.py`
理解程序有哪些模块、按钮、线程、参数、数据输出。

2. 再看 `MCUTriggerThread.py`
理解自动筛选到底是按什么顺序推进的。

3. 再看 `FastCameraThread.py`
理解程序是怎么从图像里判断“有没有合适细胞”的。

4. 最后看 `sCMOSCameraThread.py`
理解第二路相机在设计上想做什么，以及当前代码启用了多少。


## 16. 总结

这套程序本质上不是单纯“拍视频的软件”，也不是单纯“显微图像分析的软件”。  
它真正的价值在于把下面几件事闭环串起来：

- 看见细胞
- 判断细胞
- 控制芯片动作
- 继续观察结果
- 保存过程证据

因此，这个项目最核心的逻辑不是某一个算法函数，而是“多线程、多设备、多 ROI、多阶段状态切换”共同组成的实验控制流程。

如果后续你要继续维护这个项目，最优先理解的是两件事：

1. 自动筛选状态机怎么推进
2. 每个 ROI 各自承担什么任务

只要这两件事理解了，剩下的代码就会清晰很多。
